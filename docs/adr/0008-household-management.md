# ADR-0008: 家庭管理の設計方針

## Status

Accepted

## Context

FooCoはユーザーが「家庭」単位でデータを共有するアプリである。
認証（ADR-0007）の実装後、ログイン直後の家庭作成フローおよびメンバー招待の仕組みを設計する必要が生じた。
一般的なグループ機能を持つサービスのパターンを参考に、MVPとして適切な方針を検討した。

## Decision Drivers

- MVPとして実装コストを最小限に抑えたい
- 新規ユーザーが最小の摩擦でアプリを使い始められる
- 将来的なメンバー招待機能への拡張を妨げない設計にしたい
- DBスキーマ（`household_members`）はすでに複数家庭に対応している

## Considered Options

**新規ユーザーの家庭作成フロー：**

- **A. 作成 or 招待の二択**（Slack・Notion型）: ログイン直後に「家庭を作成する」か「招待リンクで参加」を選ばせる。ユーザーへの伝わりやすさは高いが、招待リンク機能の実装が必要。
- **B. 自動作成（採用）**: ログイン直後に自動で家庭を作成する。摩擦が最も少なく実装もシンプル。
- **C. 家庭なしで使える**: 家庭がなくても一部機能を使える。データモデルの複雑化を招く。

**メンバー追加の仕組み：**

- **招待リンク方式**: トークン付きURLを発行し、踏んだユーザーが自動参加。未登録ユーザーも招待可能だが実装コストが高い。
- **メールアドレス直接追加（MVP採用）**: 登録済みユーザーをメールアドレスで検索して追加。シンプルだが相手の事前登録が必要。

## Decision

### MVPの方針

**新規ユーザーの家庭作成：**
初回ログイン時（`public.users` にレコードが存在するが `household_members` にレコードがない場合）に、自動で家庭を作成し `household_members` に `role = 'owner'` で登録する。
家庭名のデフォルトは `{名前}の家庭`。後から設定画面で変更可能。

**メンバー追加：**
メールアドレスで登録済みユーザーを検索して追加する。

**複数家庭：**
MVPでは1ユーザー1家庭のみサポート。DBスキーマは複数家庭に対応しているが、UIおよびAPIは1家庭前提で実装する。

### 将来の拡張方針

案Aへのシフトとして、以下を段階的に追加する：
1. 招待リンク機能（`household_invites` テーブル、token管理、有効期限）
2. 「家庭を作成する」or「招待リンクで参加」のオンボーディング画面
3. 複数家庭の切り替えUI

## Consequences

**Positive:**
- 新規ユーザーがログイン直後にそのままアプリを使い始められる
- 実装がシンプルで Issue #23 のスコープに収まる
- DBスキーマは変更不要（既存設計で対応可能）

**Negative:**
- 相手が未登録の場合にメンバー追加できない（招待リンクで解決予定）
- 自動作成された家庭名が機械的になる（設定画面で変更必須）
